Why You Must Not Drop the Replication Slot on Shutdown

Mission: understand one TODO item deeply enough to defend it in a review · ~10 min · Source file under study: cmd/stream-process/postgres_stream_process.go

The one-sentence answer. Your wal_checkpoint row is only a client-side note of where you stopped; the replication slot is the server-side mechanism that makes PostgreSQL keep the WAL for that position. Drop the slot and your checkpoint becomes a bookmark pointing at pages Postgres is free to throw away — and any transaction committed while you were down is skipped permanently.

1. There are two bookmarks, not one

Your streamer tracks its position twice, and it’s easy to mistake one for the other:

Client-side checkpointReplication slot
Where wal_checkpoint table (your DB row) Server-side object, visible in pg_replication_slots
What it does Remembers the last LSN you persisted Tells Postgres: “retain WAL from restart_lsn onward until I consume it”
Survives restart? Yes Yes — unless your code drops it

The slot is not a connection detail. Gunnar Morling (founder of Debezium, the most widely-used Postgres CDC tool) defines slots as “Postgres’ mechanism for making sure that any segments of the write-ahead log (WAL) of the database are kept around until they have been processed by registered replication consumers” (Mastering Postgres Replication Slots). Postgres replication slots “require active acknowledgement by the consumer in order to release processed WAL segments.” The slot is the retention anchor. The checkpoint row is just a note.

2. Walk the failure through your own code

Here is your shutdown path today:

// postgres_stream_process.go:842
func (ps *PostgresStreamer) cleanup() {
	if ps.db != nil { ... }
	if ps.conn != nil {
		ps.dropReplicationSlot()   // ← the problem, line 848
		ps.conn.Close(context.Background())
	}
}

Follow a deploy or restart, moment by moment:

t0 · running @ LSN 100 Everything healthy. Checkpoint saved to wal_checkpoint. Slot retains WAL from 100 onward.
t1 · SIGTERM (deploy, crash restart, config change) cleanup() calls pg_drop_replication_slot() (line 261). Postgres is released from its obligation to keep WAL for you. Segments older than anyone else’s need may now be recycled.
t2 · downtime · a transaction commits @ LSN 150 Traffic continues against your app’s tables. No slot is holding 100–200 for you.
t3 · process restarts → createReplicationSlot() (line 129) A fresh slot is created. Per Postgres semantics, “a consumer subscribing to this slot will receive change events starting from this LSN” (creation point, say LSN 200). The new slot’s world begins at 200. It cannot reach backward.
t4 · startReplication() asks for your saved LSN 100 (line 284) loadCheckpoint() faithfully returns 100 — but the slot’s confirmed position is 200. Postgres cannot honor a start point that predates the slot’s existence. The change at 150 is never delivered. The stream resumes with a hole in it.

The cruel part: nothing looks wrong. The process starts, replication flows, your logs look clean. But wal_change is silently missing every transaction from the downtime window — and for trail-replay, a change-history tool with holes in its history is a broken product. A crash would be kinder: loud failures get fixed; silent gaps get trusted.

3. The fair objection: “aren’t leftover slots dangerous?”

Yes — and that’s exactly why drop-on-shutdown is such a tempting habit. An inactive slot keeps pinning WAL: “a replication slot could cause an unlimited amount of WAL backlog if a consumer stopped processing that slot, potentially exhausting the disk space of the database machine” (Morling, same article). In dev, dropping on shutdown gives you a clean slate. In production, you’ve traded a visible, bounded, fixable risk (disk usage, which you can monitor and cap) for an invisible, unbounded, unfixable one (lost history).

The production answer is to keep the slot and bound the risk, not to drop it:

Do

  • Create the slot once, idempotently — your “already exists, continuing…” branch (line 137) is already correct
  • Leave the slot in place on shutdown; it holds your position server-side across restarts
  • Cap retention: max_slot_wal_keep_size = 50GB (PG 13+) — Postgres invalidates an over-lagging slot rather than eating the disk (TODO L85)
  • Monitor pg_replication_slots: status, retained WAL, safe headroom — alert before pain (TODO L91)

Don’t

  • Drop the slot in cleanup() or any shutdown/signal path
  • Drop on reconnect after a network blip — transient errors are why the slot exists
  • Treat the wal_checkpoint row as sufficient — without the slot, nothing guarantees that LSN is still readable

There is exactly one right time to drop a slot: deliberate decommissioning — when the consumer is being retired for good. Morling’s housekeeping rule is to remember to drop unused slots, via an explicit admin action: SELECT pg_drop_replication_slot('...') — run by a human (or an admin command), never by a signal handler.

4. Test yourself

1 · The streamer shuts down, cleanup() drops the slot, and a transaction commits before the process restarts. What happens to that transaction’s change events?

  • They replay from the saved client-side checkpoint LSN
  • They wait inside the publication until reconnecting later
  • They never appear in the new slot’s stream
  • They get re-emitted once the new slot starts

The checkpoint is only a note; the recreated slot starts at its creation LSN and cannot reach backward. The downtime transaction falls into the gap between the old slot’s last position and the new slot’s birth.

2 · Dropping the slot makes replay from your saved checkpoint impossible because…

  • the checkpoint table is dropped alongside the slot
  • Postgres stops retaining WAL beyond the slot’s position
  • the publication forgets which tables it should publish
  • the pgoutput plugin gets uninstalled when slot drops

The slot is the retention anchor. Once dropped, WAL older than other consumers’ needs may be recycled, and a new slot only sees changes from its creation point onward.

3 · If dropping on shutdown is wrong, why does it feel responsible? What is the real risk of leaving a slot in place?

  • An inactive slot retains WAL, potentially filling disk
  • Each idle slot consumes a full backend connection
  • Old slots gradually degrade the server’s decoding performance
  • Inactive slots block autovacuum while they remain alive

Unbounded WAL retention from a stopped consumer is the classic slot failure. The fix is a bound (max_slot_wal_keep_size) plus monitoring — not dropping the slot on every shutdown.

4 · When should a replication slot be dropped?

  • During every single graceful shutdown of the consumer
  • Automatically right after each successful client-side checkpoint write
  • Whenever the consumer reconnects following a network failure
  • As an explicit, deliberate admin action during decommissioning

Dropping is a destructive, position-erasing act. It belongs behind an explicit admin command (e.g. a --drop-slot flag or SQL run by a human) when the consumer is retired — never in a signal handler.

5. Prove it on your own database (5 minutes)

Watch a change vanish

Uses the test_decoding plugin (text output, no publication needed) against your dockerized Postgres. Start it with docker compose up -d postgres, then connect: PGPASSWORD=trailpass psql -h localhost -p 5433 -U trailuser -d traildb

-- 1. Create a demo slot
SELECT pg_create_logical_replication_slot('demo_slot', 'test_decoding');

-- 2. Commit change #1, then consume it (advances the slot)
CREATE TABLE slot_demo (id int);
INSERT INTO slot_demo VALUES (1);
SELECT * FROM pg_logical_slot_get_changes('demo_slot', NULL, NULL);
-- → you see the INSERT of 1. Slot is now positioned after it.

-- 3. "Downtime" begins. A change commits while you're down.
INSERT INTO slot_demo VALUES (2);

-- 4. THE MISTAKE: your cleanup() drops the slot on shutdown
SELECT pg_drop_replication_slot('demo_slot');

-- 5. More downtime traffic, no slot retaining anything
INSERT INTO slot_demo VALUES (3);

-- 6. "Restart": recreate the slot
SELECT pg_create_logical_replication_slot('demo_slot', 'test_decoding');

-- 7. New traffic after restart
INSERT INTO slot_demo VALUES (4);

-- 8. Consume: what do you get?
SELECT * FROM pg_logical_slot_get_changes('demo_slot', NULL, NULL);
-- → ONLY the INSERT of 4. Rows 2 and 3 are gone from the stream
--   forever — yet they sit happily in the table. That is the silent hole.

-- 9. Contrast (optional): repeat steps 1–3 but SKIP the drop.
--    get_changes now returns row 2. The slot held it for you.

-- 10. Clean up
SELECT pg_drop_replication_slot('demo_slot');
DROP TABLE slot_demo;

Contrast step 9 is the whole lesson in one query: the only difference between “row 2 survives a restart” and “row 2 vanishes” is whether the slot was dropped.
